在做后台业务开发时，经常会遇到一类需求：用户的操作本身很快，但后续需要挂载一长串耗时较长、且极度依赖外部第三方接口的处理链路。

最近我在业务里完整梳理并重构了这样一个场景：候选人在官网投递简历，系统接收后调用大语言模型完成简历解析与结构化评分，最后将评估结果推送到对应岗位负责人的飞书工作群与管理后台。

这篇文章梳理了该链路的完整设计方案，重点讨论在外部依赖不稳定、网络可能抖动以及节点随时可能重启的前提下，如何通过异步解耦保障数据的可靠性与一致性。

---

## 一、业务场景

从业务视角来看，整个处理流程主要包含四个阶段：

1. **简历接收**：候选人在官网填写表单、上传附件并提交。该接口对响应速度要求极高，必须在数十毫秒内给用户明确的“提交成功”反馈。
2. **数据持久化**：系统完整记录候选人基本信息、附件位置、投递渠道与初始业务状态。
3. **模型评分**：系统需要对简历内容进行深度提取，并调用大语言模型结合岗位画像进行打分。该过程通常需要数秒至数十秒，且外部模型服务的可用性存在天然波动。
4. **多端协同通知**：评分产出后（无论是正常出分还是异常报错），系统需要将结构化结果通过即时通讯工具（飞书）同步给该岗位的一位或多位负责人，同时确保管理后台前端能及时展示最新的候选人记录。

如果将上述逻辑全部揉进一个同步请求中处理，外部模型的长耗时与接口抖动将直接摧毁投递入口的可用性。因此，整条链路必须全面异步化。

---

## 二、核心机制与概念

在讨论具体方案前，有三个核心机制是构建整套异步体系的基础：

### 1. 异步 Worker（后台工作进程）
将 Web 接口与长耗时任务彻底解耦的常驻工作进程。Web 服务只负责接收请求并生成任务标记，随后立即向用户返回响应；Worker 进程则在后台独立运行，负责从任务队列或数据表中获取待办任务并执行具体的重量级业务。这样即便外部处理耗时几分钟，也不会占用或阻塞面向用户的网络连接。

### 2. Transactional Outbox（事务性发件箱模式）
为了防止“业务数据存入了数据库，但消息未成功发出”导致的系统不一致问题，Transactional Outbox 模式要求：**业务主表数据的更新，与待触发任务的写入，必须封装在同一个本地数据库事务内完成**。  
借由数据库自身的 ACID 特性，两者要么同时生效，要么同时回滚。只要业务数据写入成功，系统就必然存在一条待处理的任务记录，从根源上杜绝了消息丢失的隐患。

### 3. Webhook（事件回调）
现代办公协作工具（如飞书）通常提供标准的 HTTP 推送入口。业务系统无需建立复杂的双向长连接，只需将格式化好的富文本或交互卡片数据，以 HTTP POST 方式发送到平台指定的 Webhook 地址，即可实现机器人的即时消息分发。

## 三、方案架构与流转时序

整套架构围绕“快速落盘、解耦执行、故障自愈、状态可控”的目标进行设计，整体流转时序如下：

```text
候选人          官网服务          数据库事务        AI Worker       通知 Worker       飞书/HR端
  │                │                 │               │                │               │
  │── 1. 提交简历 ─>│                 │               │                │               │
  │                │── 2. 保存简历 ──>│               │                │               │
  │                │── 3. 写入事件 ──>│ (同事务提交)   │                │               │
  │<── 4. 提交成功 ─│                 │               │                │               │
  │                │                 │               │                │               │
  │                │── 5. 实时通知 ──────────────────>│                │               │
  │                │                 │               │                │               │
  │                │                 │<─ 6. 租约抢占 ─│                │               │
  │                │                 │  (标记处理中)  │                │               │
  │                │                 │               │── 7. 调模型打分 │               │
  │                │                 │               │<── (得到结果) ──│               │
  │                │                 │<─ 8. 写入评分 ─│                │               │
  │                │                 │<─ 9. 写通知箱 ─│ (同事务提交)   │               │
  │                │                 │               │                │               │
  │                │                 │<────── 10. 轮询待发通知 ───────│               │
  │                │                 │               │                │── 11. 发送 ──>│ (飞书卡片)
  │                │                 │<────── 12. 标记已发送 ─────────│               │
  │                │                 │               │                │               │
  │                │                 │ (页面静默刷新) │                │               │
  │                │                 │<───────────────────────────────────────────────│ (管理后台)
```

### 1. 入口保护：基于 Outbox 的原子持久化
官网收到投递请求后，仅做基础的字段校验。随后在同一个数据库事务中执行两项写操作：
- 将候选人信息与附件信息写入投递主表；
- 写入一条代表“简历已入库，待启动评分”的任务记录至 Outbox 事件表。

事务提交后立刻向候选人返回投递成功响应。整个入口处理被压缩为单纯的数据库单次提交，耗时极短且抗压能力极高。

### 2. 双轨驱动：实时唤醒为主，定时对账兜底
如何确保 Outbox 中的任务能被及时处理，同时防止漏跑？系统采用了“快慢结合”的双轨机制：
- **实时唤醒（快轨）**：事务提交后，Web 服务随即向后台发起一次轻量的内部调用，以毫秒级时延驱动 Worker 立即介入处理，保证常规情况下的流转速度。
- **定时对账（慢轨）**：常驻对账服务每隔固定周期扫描一次数据，检索“已创建超过阈值时间但仍处于未分配状态”的历史记录。这一步用于兜底因网络瞬断、容器发版重启等意外造成的实时调用丢失，确保任务零遗漏。

### 3. AI Worker 执行：并发控制与租约抢占
大模型调用是典型的 I/O 密集型耗时操作，Worker 的调度机制包含以下设计：
- **批量获取与并发分发**：Worker 一次性从数据库检索一批待评分任务，将其分配到设定的并发槽位中并行执行，最大化吞吐效率。
- **分布式租约（Lease）**：Worker 抢占任务时，通过条件更新将任务置为“处理中”，并写入一个到期时间戳（租约有效期）。其他并发节点跳过该任务。若当前 Worker 在调用过程中因机器故障异常退出，租约到期后该任务将自动被其它健康 Worker 识别并重新抢占接管，实现故障自愈。
- **状态收敛**：无论大模型成功返回，还是经历重试后依然超时/解析失败，Worker 都必须将最终结论写回任务表，形成明确的最终状态（“成功”或“失败”）。

### 4. 细粒度通知：按负责人裂变与独立幂等
打分完成后，评分 Worker 不直接调用飞书接口，而是将通知也做成独立的 Outbox 任务：
- **按负责人拆分任务**：一个岗位通常配置了多名负责人（如多位用人部门面试官与 HR）。系统会为每位负责人单独创建一条独立的通知任务。
- **独立幂等键**：每条任务绑定由“评分任务唯一标识 + 负责人标识”组合而成的幂等键。
- **独立重试**：独立的通知 Worker 负责读取该任务表并调用飞书 Webhook。若某个负责人的消息因网络异常发送失败，只会针对该负责人单条重试，既不阻塞其它负责人的通知投递，也不会造成已成功接收人员被重复消息轰炸。

### 5. 前端感知：静默刷新与生命周期监听
为了让管理后台的用户无缝看到最新进展，前端配合采取了被动感知策略：
- 维持低频的静默轮询更新数据，不触发全屏加载动画，不打乱用户当前的表格勾选状态与滚动条位置。
- 监听浏览器的 `visibilitychange` 和 `focus` 事件。当 HR 收到飞书消息、由飞书客户端切换回浏览器管理后台标签页时，系统立刻主动发起一次增量拉取，确保界面显示始终为最新。

## 四、为什么采用这种设计？

这套方案并没有引入复杂的分布式中间件集群，而是基于关系型数据库与明确的状态流转解决了可靠性问题，其核心考量主要体现在四个维度：

### 1. 严格隔离外部不可控风险
外部大模型的响应延迟（数秒至几十秒）以及协同工具接口的偶发网络抖动，属于系统无法完全控制的“外部依赖风险”。通过事务性 Outbox 与后台 Worker，系统在物理层面将“用户投递主流程”与“后续计算和通知流程”隔离开来。外部服务的不可用不会对投递入口造成任何影响。

### 2. 杜绝业务状态的静默丢失
长链路系统最容易出现的问题并非报错，而是由于逻辑未闭环导致的数据停滞。  
在本方案中，“评分失败”被定义为一种标准的最终状态。当模型重试达到上限仍未成功时，系统会明确落盘失败状态、在后台标记警示，并通过飞书告知负责人“AI 评分未完成，请人工查看”，同时提供手动重试入口。系统允许特定环节发生异常，但必须保证整个流转过程始终处于可感知、可干预的受控状态。

### 3. 精细化的容错与幂等重试
* 租约机制解决了多节点并发冲突以及单节点崩溃导致的任务死锁问题。
* 通知任务按负责人粒度裂变，配合复合幂等键，将重试的爆炸半径收敛到了单个消息级别。任何一个节点的瞬时失败，都可以通过针对性的局部重试恢复，而不会引发连锁反应。

### 4. 低成本兼顾性能与确定性
如果仅靠定时轮询，任务的整体推进会有明显的滞后感；如果完全依赖事件的即时推送，又无法保证瞬时故障下的百分之百送达。方案采用“实时推送驱动常态流转，定时对账扫描保障最终一致”的双引擎模型，用极低的代码与运维成本，换取了兼具高响应度与高确定性的系统表现。
