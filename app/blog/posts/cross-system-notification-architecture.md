在平时做业务开发时，经常会遇到这类需求：自己这边的系统发生了一件事，得通知到另一个系统里的人。比如招聘系统收到了新简历，要在飞书上给面试官发一条消息；或者每天早上九点，把前一天的数据汇总推给业务负责人。

以前我觉得这种需求顺手调一下对方接口就行了，但后来线上出了几次小事故才发现：只要跨了系统，网络超时、服务重启、重复触发这些问题就一定会发生。

这篇文章想梳理一下，把这种跨系统通知真正做稳，底层到底该怎么设计。

---

## 一、业务场景与核心矛盾

这类通知在业务上主要有两种形态：

1. **实时触发**：系统刚发生一个动作，就得立刻通知对方。比如候选人提交了简历，面试官要在几秒内收到飞书提醒。
2. **定时汇总**：每天固定时间跑一次统计，把前一天的业务进度打包发给对应的负责人。

这两类场景看着都不复杂，但在工程实现上会遇到两个很讨厌的矛盾：

* **如果直接同步调用**：主业务（比如保存简历）就得等着飞书接口返回。飞书如果卡两秒，整个系统就跟着卡两秒；如果飞书挂了，难道把用户已经保存成功的业务数据也回滚掉吗？如果不回滚，这期间程序突然重启，通知不就凭空消失了？
* **如果直接异步重试**：遇到网络超时，请求其实可能已经发到对方服务器了，只是响应没传回来。一旦盲目重试，用户就会连续收到两条一模一样的消息轰炸。

要解决这些问题，必须把“业务处理”和“消息发送”彻底拆开。

---

## 二、先把这几个概念讲清楚

为了解决上面的矛盾，有三个核心机制是整套设计的基础：

### 1. 事务性发件箱（Transactional Outbox）
这名字听着挺大，其实逻辑特别朴素：  
业务系统在保存自己的核心数据时，**顺便把要发送的通知也当成一条普通的数据库记录，放在同一个数据库事务里一起保存**。

因为在一个事务里，数据库的底层机制能保证两者要么一起存成功，要么一起失败。只要业务数据存下来了，发件箱里就肯定有一条待发送的任务，哪怕服务器下一秒断电重启，这条通知也不会丢。

### 2. 异步 Worker（后台工作进程）
Worker 就是一个在后台默默运行的独立程序，不处理任何用户前端的请求。  
它的职责非常单一：去发件箱表里找那些还没发出去的任务，然后调飞书接口把消息发出去。这样一来，即使飞书接口变慢或者临时不可用，也只会影响 Worker 自己的重试节奏，完全不会连累上游的主业务系统。

### 3. 幂等键（Idempotency Key）
在网络世界里，“请求超时”并不代表“对方没收到”。  
为了防止重试导致重复发消息，我们需要给每条通知生成一个全局唯一的身份证号，比如用 `通知类型 + 业务日期 + 接收人ID` 拼成一个字符串。不管这个任务因为超时重试了多少次，系统只要认准这个标识，就知道这是同一条消息，不会重复推给同一个用户。

---

## 三、具体的方案与实现逻辑

这个方案的核心思路，就是**把原来一步到位的调用拆成两段**：上游业务只负责把要发的消息写进数据库，后面的网络调用和重试全权交给独立的后台 Worker 去跑。

整个流转逻辑分成四个阶段：

1. **业务先落盘，连带记下通知**：当业务事件发生时（比如候选人投了简历），系统把业务数据写进数据库的同时，在同一个事务里往“通知任务表”塞一条待发送记录。事务只要提交成功，主流程就可以直接给用户返回“操作成功”，不用管通知到底发出去了没有。
2. **通知 Worker 领任务去发**：后台的 Worker 发现有新任务，先把这条记录的状态改成“发送中”，然后调飞书接口去发消息。这一步把状态改成“发送中”，是为了防止别的节点或者线程重复拿到同一条任务。
3. **根据接口返回更新状态**：飞书如果正常返回成功，Worker 就把状态改成“已发送”，这条任务就彻底跑完了。
4. **遇上异常就退避重试**：如果调用飞书超时了，Worker 就把记录的状态打回“待重试”，并记下具体的错误原因，等过一会儿再试。如果连着重试了几次依然不成功，再把它改成“最终失败”，等人工来处理。

整个过程的时序图如下：

```text
业务发起端         业务数据库事务       通知任务表 (Outbox)       通知 Worker        飞书平台 / 接收人
    │                  │                      │                    │                  │
    │── 1. 核心业务 ──>│                      │                    │                  │
    │── 2. 生成通知 ──>│ (同一个事务落盘)      │                    │                  │
    │                  │                      │                    │                  │
    │<─ 3. 立即返回 ───│                      │                    │                  │
    │                  │                      │                    │                  │
    │ (发内部信号快速唤醒) ───────────────────────────────────────>│                  │
    │                  │                      │                    │                  │
    │                  │                      │<─ 4. 取出待发任务 ─│                  │
    │                  │                      │   (状态置为发送中) │                  │
    │                  │                      │                    │── 5. 调用接口 ──>│
    │                  │                      │                    │<─ 6. 返回成功 ───│
    │                  │                      │                    │                  │
    │                  │                      │<─ 7. 标记已发送 ───│                  │
    │                  │                      │                    │                  │
    │                  │                      │   [如果步骤6超时]  │                  │
    │                  │                      │<─ 8. 记录失败原因 ─│                  │
    │                  │                      │   (稍后按退避重试) │                  │
```

在落地这套逻辑时，还有几个细节是必须做扎实的：

### 1. 算归算，发归发
* **对于实时通知**：上游业务把正式数据和通知任务存进数据库后，就算完事了。接着通过一个简单的内部调用去唤醒 Worker，让 Worker 马上把消息送出去。这样端到端只有几百毫秒的延迟，但两个系统的依赖彻底解开了。
* **对于定时汇总**：定时任务只负责“在几点钟、把哪些数据算出来、分别发给谁”，算完后把一批任务直接塞进通知表，它的工作就结束了。真正的发送依然交给 Worker 去排队发。哪怕有上千人要通知，定时任务也不会因为挨个调接口而卡死超时。

### 2. 状态机与可控重试
每条通知在表里都有明确的状态：`待发送`、`发送中`、`已发送`、`失败`。  
如果遇到网络波动导致调用失败，Worker 会记录下失败的原因，并按指数递增的时间间隔（比如过 5 秒、15 秒、1 分钟）去重试。如果重试了几次依然不成功，就把它打上`最终失败`的标签，停下来等待人工查看，避免无休止地消耗系统资源。

### 3. 排查问题不要靠猜
以前经常有人问：“为什么我今天没收到通知？” 如果没有留痕，查起来往往很痛苦。  
有了这套机制，排查路径就变得非常清晰：
* 数据库里有没有生成这条记录？如果没有，说明是前置业务没有触发，或者定时任务统计出的结果为零。
* 状态是不是一直停在“待发送”？如果是，说明 Worker 可能卡住了或者积压了。
* 状态是不是“失败”？如果是，直接看记录里存下的第三方返回报错即可，几分钟就能定位是权限掉了还是参数不对。

### 4. 容易踩坑的两个细节
* **时区问题**：定时任务在算“昨天”的数据时，千万不要随手取操作系统的默认时间。一旦服务器迁移或者容器时区配置成了 UTC，算出来的日期就会差整整 8 个小时，业务数据直接错乱。必须在代码里显式写死使用业务对应的时区。
* **通知里的跳转链接**：通知里通常带一个跳转到后台的链接，这个地址一定要从环境变量里读。测试环境跳测试系统，生产环境跳生产系统，不能直接把线上地址写死在消息模版里。

## 四、为什么最后选了这套方案？

回头看这套设计，其实并没有用什么高深复杂的技术，就是通过关系型数据库加一个常驻 Worker 把链路理顺了。这样设计主要换来了三样东西：

1. **主业务的可用性**：不管飞书或者其他第三方平台抖成什么样，只要我自己的数据库还在，主流程就能正常运转，不会被外部依赖拖死。
2. **通知的确定性**：靠本地事务保证“任务一定能记下来”，靠幂等键保证“就算重试也不会重复发”，靠状态流转保证“不管是成功还是失败，都有据可查”。
3. **极低的运维心智负担**：不需要在最开始就上一整套庞大复杂的消息中间件集群。对于绝大多数业务系统来说，用一张数据表加一个后台任务，就已经足够稳定地扛住日常的所有跨系统交互了。
