> 这是一篇关于服务器磁盘告警排查，以及把文件上传链路推倒重构的学习笔记。  
> 核心不讲死概念，而是把“为什么磁盘会写满”、“为什么后端转发大文件是灾难”、以及“前端直传怎么做才安全”这套逻辑用大白话彻底理顺。

---

## 一、服务器磁盘在狂写，先别慌

服务器磁盘使用率飙升时，第一反应往往是：“是不是被黑了？还是哪个程序在偷偷塞文件？”  
其实后台程序往磁盘写数据再正常不过，常见的来源无非这么几类：

*   **各种应用日志**：请求访问日志、系统错误日志、业务埋点；
*   **上传的临时缓存**：用户上传大文件时，Web 框架在后台偷偷把数据存到了系统的临时目录里；
*   **本地存储与轻量数据库**：比如 SQLite、本地搜索索引、本地队列文件；
*   **构建或运行缓存**：前端打包出来的静态资源、Python 的缓存文件。

排查磁盘告警时，顺着这三个问题摸排就够了：
1.  **到底是谁在写？** 用 `iotop`、`pidstat -d` 抓出当前正在大量写入的进程 PID；
2.  **它写到了哪里？** 用 `lsof -p <PID>` 配合 `ps -fp <PID>`，看清楚这进程到底跑在什么目录下、在往哪个文件狂写，核对是不是自己的正常业务；
3.  **这些写进去的文件有人管清理吗？**

在这次排查中，大量写盘的其实就是我们自己的 Python Web 进程，属于正常处理请求。真正的病根不在于“它写了盘”，而在于**这些写进去的文件生命周期根本没人管**。

## 二、日志轮转：为什么不能让日志一直追加？

很多新手上线项目时，喜欢把日志一股脑直接追加写进 `access.log` 或 `error.log`。短期内没问题，但只要时间一长，这个单文件就会从几兆膨胀到几十个 G，直到把整块磁盘硬生生撑爆。

所谓的**日志轮转（Log Rotation）**，逻辑其实特别朴素：  
当一个日志文件写到指定大小（比如 100MB）或者到了新的一天，系统就自动把它改个名字归档（比如改成 `access.log.1`），然后新建一个空白的 `access.log` 接着写。超过一定天数（比如 14 天）的历史日志，系统就自动压缩或者清理掉。

```text
access.log           --> 当前正在写入的新日志
access.log.1         --> 昨天的日志
access.log.2.gz      --> 前天的日志（已被系统自动压缩归档）
```


它的本质就是：**既保留出问题时回溯日志的能力，又给日志占用的空间划上一道死线**。  
如果系统接入了 `systemd-journald`，必须配置存储上限；如果是应用自己打日志文件，就必须配上 `logrotate` 或自带的滚动策略，绝不能放任日志裸奔无限追加。

## 三、FastAPI 上传大文件的坑：临时盘和内存的双重夹击

很多刚接触 Web 开发的人，处理文件上传的代码大概都长这样：

```python
# 典型的危险写法：
# 1. 大文件上传途中，框架默默往临时磁盘写缓存
# 2. 调用 read() 时，把整份文件一口气全加载进 Python 内存
# 3. 再通过后端把这几百兆网络流转发给 OSS
```


看起来稀松平常，但背后藏了两个致命陷阱：

1.  **偷偷占磁盘**：前端发过来的通常是 `multipart/form-data` 请求。框架（如 FastAPI 底层的 Starlette）在接收时有个阈值，小文件直接在内存里抗，一旦文件超过阈值，框架为了防止内存崩掉，会**自动把数据落到系统的临时磁盘目录里**。
2.  **瞬间拉爆内存**：当代码里调用 `await file.read()` 时，又把已经落在临时盘上的大文件**一次性完整读进了 Python 内存**。
3.  如果同时有 10 个人在上传 200MB 的作品集，系统一瞬间就需要消耗：
    **并发数 × 单文件大小 ≈ 10 × 200 MB = 2 GB 内存**

并发一上来，操作系统的 OOM 机制就会直接把整个后端进程干掉。

这里必须分清两个概念：
*   **磁盘占用累积**：文件上传产生的临时文件没有及时删干净，随着时间推移像滚雪球一样把磁盘挤满；
*   **瞬间内存峰值**：大文件被一次性整个读进内存，请求期间瞬间把可用内存吃光，并发一高进程就崩溃。

## 四、破局之道：把大文件绕过后端，让浏览器直传 OSS

既然大文件经过业务服务器又吃磁盘又吃内存，那为什么非得让业务服务器当“二道贩子”呢？

传统模式和直传模式的本质区别如下：

```text
【传统模式】（后端扛所有压力）
浏览器 ──────> 业务服务器 ──────> 对象存储 (OSS)
               (又占磁盘又占内存)

【直传模式】（后端只管开凭证）
浏览器 ──(1. 申请一次性上传凭证)──> 业务服务器 (耗时几毫秒，不碰文件)
浏览器 ──(2. 真正的大文件二进制流)──> 对象存储 (OSS) (大流量直接打给云厂商)
浏览器 ──(3. 上传成功凭证)────────> 业务服务器 (保存业务记录)
```


直传的核心逻辑是：**业务服务器只做鉴权和记账，庞大的文件传输流量直接由底盘极大、带宽极高的云厂商 OSS 去承接**。业务服务器的带宽、内存和磁盘瞬间得到彻底解脱。

但直传**绝不是**直接把 OSS 的 AccessKey 账密写死在前端。这会导致存储桶任何人都能随便读写，是严重的安全灾难。

## 五、直传怎么做才安全？拆开“传文件”与“业务确认”

真正的安全直传必须设计成一套**“上传意图（Upload Intent）”闭环**：

### 1. 意图申请（向后端拿钥匙）
前端告诉后端：“我是用户张三，我想传一个 15MB 的 PDF 简历”。  
后端校验身份、格式和文件大小后，生成一个**只在 5 分钟内有效、且只能传到指定临时路径（如 `pending/xxx.pdf`）的预签名 URL**，顺便给前端颁发一个包含校验哈希的一次性凭证（Token）。

### 2. 浏览器直接推流给 OSS
前端拿到这个预签名 URL 后，直接用原生 HTTP 请求把文件二进制流通过 `PUT` 发给 OSS。整个过程完全不经过业务后端，后端的内存和磁盘波澜不惊。

### 3. 回调确认（把钥匙换成正式数据）
前端上传成功后，拿着凭证找业务服务器交差：“我传完了，请确认”。  
后端此时**绝不能只听前端的一面之词**，而是要在后台向 OSS 发起一次轻量的 `HEAD` 查询：核对文件是不是真的存在？大小是不是吻合？文件类型是不是被篡改了？确认无误后，把文件从 `pending` 临时目录移至正式目录，并在数据库里写下业务记录。

这套设计守住了几个关键安全边界：
*   凭证必须跟当前用户绑定，别人拿到也用不了；
*   时效极短，过期自动失效；
*   OSS 上的 `pending/` 目录配置生命周期规则，那些拿了凭证却没真正传完的半吊子垃圾文件，几天后由 OSS 自动清理，绝不浪费空间。

## 六、顺带理清：内存峰值 vs 内存泄漏

在排查这类系统瓶颈时，还有一个概念最容易被搞混：**大文件造成的内存抖动，并不是内存泄漏**。

*   **内存峰值**：代码一次性读了 500MB 文件，内存瞬间飙升；但请求结束、垃圾回收跑完之后，这部分内存会老老实实还给操作系统。这属于代码设计不合理导致的高峰，不是泄露。
*   **内存泄漏**：代码里写了一个全局变量（比如为了图省事把请求信息全 `append` 到一个全局 list 里），导致即使请求早就结束了，对象依然死死被全局变量引用着，垃圾回收器根本不敢回收。进程的内存只增不减，跑几天就必然 OOM 崩溃。

面对这种问题，我的排查套路是：
1.  **先看趋势**：看监控面板，内存是只在大请求进来时“脉冲式飙高”，还是没有任何大流量也在“阶梯式单调递增”？
2.  **管好容器与兜底**：全局缓存必须加上最大容量限制（比如使用定长队列 `deque(maxlen=1000)`）；
3.  **上道安全绳**：生产环境把 Gunicorn 的 `max-requests` 打开，让单个 Worker 进程在处理了几千次请求后自动无感重启一次，及时清理长久运行产生的内存碎片。

## 七、总结与复盘

回头复盘这次磁盘告警和架构改造，最深刻的体会就是**不要头痛医头**：

*   **看到磁盘在写**：先找清楚是哪套进程、哪个目录在写，别把正常的框架临时缓存当成异常入侵，抓出日志轮转缺失和临时目录生命周期才是正解。
*   **看到大文件流转**：果断放弃让业务服务器在中途转发的做法，**全面转向浏览器直传 OSS**，把文件二进制流从脆弱的应用进程里剔除出去。
*   **把安全抓在手里**：做前端直传不是放权，通过“短时签名 URL + 服务端后台元数据二次核对”，既享受到直传的性能，又牢牢守住权限和文件校验底线。
